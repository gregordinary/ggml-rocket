# ggml-rocket on the RK3576

On the RK3576 the backend runs [the RK3576 route](README.md#terms): an int8 W8A8 matmul with a
per-output-column requant on the NPU. It is the only matmul route on that part. The RK3588 fp16,
int8, int4 and bf16 routes refuse there by construction. The backend therefore claims a matmul on
the RK3576 for the RK3576 route or declines it.

> [!CAUTION]
> A run on the RK3576 must set `ROCKET_INT8=1`. Without it, `supports_op` declines every
> `MUL_MAT`, and a run at the defaults offloads nothing and reports no reason. Run once with
> `ROCKET_LOG_STDERR=1` to confirm the offload.

The backend selects the route from the detected part, not from an environment variable. Build it
with `-DGGML_ROCKET_NATIVE_FP16=OFF` for the RK3576, because the default convert kernels target
the RK3588's `armv8.2-a+fp16` baseline.

## The route

The RK3588's int8 route returns a raw int32 accumulator, and the host applies both scales. The
RK3576 route instead calls that part's int8-output entry, which requantizes each output column in
the DPU epilogue by a scale the host supplies. The route has four parts, and each is required:

1. **Rotation.** The route rotates `A` and `B` by an orthonormal Hadamard matrix along `K` on
   every call, whatever `ROCKET_INT8_HADAMARD` says. An unrotated run is chaotic: a 2% change in the per-column divisor moved one model's perplexity by nine orders of
   magnitude.
2. **Quantization.** `A` is quantized per tensor and `B` per output channel.
3. **Per-column output requant.** Its scale is frozen after a short calibration and divided by a
   safety factor (`ROCKET_RK3576_NCAL`, `ROCKET_RK3576_CALSAFE` and `ROCKET_RK3576_BOOTMARGIN`).
4. **Host dequantization.** The host dequantizes by the scale it asked the entry for, not by the
   gain the entry's integer ramp delivered. The two differ by the entry's `worst_rel_err`, and
   dequantizing by the delivered gain measured no net difference.

Together, the four parts give this perplexity against the per-tensor output scale they replace:

| Configuration | Qwen2.5-1.5B | SmolLM2-1.7B |
|---|---:|---:|
| The RK3576 route | 1.008x | 1.020x |
| Per-tensor output scale | 1.11x | 2.26x |

**Conditions:** wikitext-2 perplexity against fp32, simulated on the host with an exactly frozen
column maximum [host-computed 2026-08-10]. SmolLM2-1.7B's figure is at a `ROCKET_RK3576_CALSAFE`
of 2.0, and Qwen2.5-1.5B's is the same at 2.0 and 3.0.

On the device, the route measures 1.011x wikitext-2 perplexity on Qwen2.5-1.5B F16. Its perplexity
is 9.8969, against 9.7872 for the same GGUF on the CPU backend [HW sweep 2026-08-11, H96 MAX M9,
llama.cpp b10356]. The eight chunks measured have an error bar of ±0.59. That figure uses the default calibration
(`ROCKET_RK3576_CALSAFE`=3.0) and is against the CPU backend rather than fp32, so do not compare it
with the host-computed table.

`ROCKET_RK3576_AROW=1` replaces the per-tensor activation scale with one per row. Per-row scales
cost nothing at this interface and score better on every per-GEMM norm. End to end they raised
SmolLM2-1.7B's wikitext-2 perplexity from 25 to 964 against the per-tensor scale, 38x, and did
not raise Qwen2.5-1.5B's. Measure a candidate model end to end before setting it.

To be claimed for the RK3576 route, a matmul must meet these conditions, which are stricter than
the RK3588's:

- `K%32` and `N%32`, where the RK3588 needs `N%16`
- `K >= 64` and `N >= 32`
- A 2D static weight of type F16 or F32, with an F32 activation and output. A quantized or BF16
  weight is declined
- `M >= ROCKET_MIN_M`
- A chunking of `K` that the entry accepts (see [Splitting K](#splitting-k))

`M` has no alignment constraint on this part, and `M=1` computes. The backend declines
`MUL_MAT_ID` on the RK3576 whatever `ROCKET_MOE` is set to, so a MoE model's expert ops run on the
CPU. It also declines `FLASH_ATTN_EXT`, because `librocketnpu` has no attention encoder for this
part. Attention runs on the CPU backend's own kernel, with no setting needed.

## Performance

On Qwen2.5-1.5B at `pp2048`, the RK3576 route measures 13.36 t/s:

| Configuration | t/s | RK3576 route speedup |
|---|---:|---:|
| The RK3576 route | 13.36 | |
| ggml's `Q8_0` CPU kernel | 10.18 | 1.31x |
| The same F16 GGUF on the CPU backend | 5.64 | 2.37x |

**Conditions:** RK3576 (H96 MAX M9), kernel 7.1.7, `rocket` 1.6.0, stock llama.cpp b10558, `-ub`
512 [HW sweep 2026-08-23]. Four CPU threads pinned to the A72 cores, governor `performance`,
attention on the CPU. The governor setting moves the route's rate by 16%.

Quote the two ratios together, because they answer different questions. The 2.37x is the speedup
a drop-in user sees, because the route consumes an F16 GGUF. The 1.31x is against the fastest
CPU configuration on the same part.

> [!NOTE]
> A `pp512` figure on the RK3576 mixes the calibration and the converged route. With
> `ROCKET_RK3576_NCAL` at 2, the warm-up forward and the first timed rep calibrate, and the later
> reps run converged. Its 11.78 t/s averages the two [HW sweep 2026-08-11]. Compare the route at
> `pp2048 -ub 512`, where every timed rep is converged.

## Calibration

Each calibration forward runs two device passes. Pass one estimates the per-column accumulator
maxima from an analytic bound. Pass two refines them at that scale and returns the output.

`ROCKET_RK3576_CALSAFE` defaults to 3.0 because the frozen maximum comes from this calibration,
which has a 0.3% per-column error. At 2.0 that error costs SmolLM2-1.7B 0.018 of perplexity ratio,
against 0.0021 at 3.0. With an exactly frozen maximum, the ratio moves only 0.0017 between the two
values.

## Splitting K

The entry refuses a `K` of 6176 or more, which an FFN down-projection reaches. By default the
backend declines such a matmul, and the CPU computes it. `ROCKET_RK3576_KSPLIT` cuts it into
chunks on the host, one whole W8A8 GEMM each, and sums the f32 partials. The split is fast and
exact, but it puts `ffn_down` on the route, an input its per-tensor activation scale does not fit.
Qwen2.5-1.5B's wikitext-2 perplexity rises from 9.90, with the down-projections on the CPU, to
15.84 [HW sweep 2026-08-11]. More chunks raise the cost: cut ten ways, the same
projection scores a perplexity of 18.22, against 15.84 cut four ways.

## Profiling

`ROCKET_MM_PROFILE` also reports this route, through a third accumulator. The report has the
library's buckets (`sumabs / packA / packB / coeff / gen / alloc / stamp / submit / wait / read`)
and the terms outside the entry (`valloc / quant+rot / calibrate / entry / dequant`).

The same line is followed by one row per GEMM shape `(M, Kc, N)`, over converged calls only. Each
row gives `quant+rot`, `entry`, `dequant` and `cvt16` per call. It also counts the calls whose
activation was the previous call's, which rotate and quantize the same activation again. On a
transformer those are `k` and `v` after `q`, and `up` after `gate`.

Both reports sum to the time of the offloaded matmuls, not to prefill time. Attention, the norms,
rope and the scheduler are in neither.
